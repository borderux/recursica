# TimePicker Implementation Notes

## Architecture Overview

Unlike every other input in `mui-adapter`, `TimePicker` wraps `@mui/x-date-pickers`'s `TimePicker` (not a plain `@mui/material` primitive). This was a deliberate choice (Matt Massey, 2026-08-07) over a native `<input type="time">`, in exchange for a real clock/list-based time selection UI at the cost of a new dependency (`@mui/x-date-pickers` + `dayjs`, both added as optional peer deps + a real `dayjs` dependency).

## Structural Constraints

1. **Value type boundary**: the public `value`/`defaultValue`/`onChange` API is a plain `"HH:mm"` (or `"HH:mm:ss"` with `withSeconds`) string, matching `mantine-adapter`'s `TimeInput`-based convention exactly. Internally this component converts to/from a `dayjs` instance at the boundary (`toDayjs`/`.format()`) — `dayjs` never leaks into the public props.
2. **Self-contained localization**: `<LocalizationProvider dateAdapter={AdapterDayjs}>` is wrapped **locally inside this component**, not at `RecursicaThemeProvider` or app-root level. This keeps `TimePicker` a drop-in component with zero setup burden on consumers; `@mui/x-date-pickers` explicitly supports nested/local `LocalizationProvider`s for exactly this use case.
3. **`variant="standard"` field, not `"outlined"`**: MUI X's default field renders `PickersOutlinedInput`, which draws a "notched outline" (an SVG-legend cutout for a floating label). Since Recursica never uses the library's native label (labels are owned entirely by `FormControlWrapper`), the notched-outline mechanism has no label to route around and is unnecessary complexity to fight. Using `variant="standard"` (`PickersInput`) instead gives a much simpler DOM to restyle, at the cost of suppressing its native underline decoration (`::before`/`::after`) so our own `.root` border can apply instead.
4. **No `slots`/`classes` prop like other components**: as of `@mui/x-date-pickers` v9, the field always renders the newer "accessible field" DOM structure (individual clickable spans per section) — there is no `enableAccessibleFieldDOMStructure={false}` fallback to a plain `TextField`/`InputBase` anymore. Styling is done via `slotProps.field.className` (attaches our `.root` class to the field wrapper) plus global-selector overrides on MUI's own stable generated classnames (`:global(.MuiPickersInputBase-sectionsContainer)`, etc.) — a different mechanism from every other component in this adapter, which all target `InputBase`'s simple `classes` prop directly.
5. **`error` isn't a native field prop**: unlike core MUI inputs, the field slot has no direct `error` boolean prop wired to visual state the same way `InputBase` does. `TimePicker.tsx` sets `data-error="true"` explicitly via `slotProps.field`, and the CSS module targets that attribute directly rather than relying on an MUI-managed `.Mui-error` class.
6. **Known limitation — the popup clock/list view is unstyled**: this pass covers the closed-state field only (border, background, text, focus/error/disabled). The open dropdown (digital clock list or analog clock, depending on `views`) still renders with MUI's default theme, not Recursica tokens — there's no Figma-exported token set for it (mirrors the same category of gap `DatePicker`'s calendar popover has in `mantine-adapter`). Revisit once there's a design spec for it.
7. **Read-Only Implementation**: `readOnlyType="text"`, matching `DatePicker`'s convention.
